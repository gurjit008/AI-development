V3 is primary new form; preserve older-version forms, fields and inventory structure. No production deployment or destructive operations authorized. Existing agent instructions do not dictate an application stack.

## Functional requirements

1. Explicit local account authentication with engineer/reviewer/admin roles. Engineer owns authored reports; reviewer reads all reports and appends comments; admin reads/edits all, manages users and inventories. Roles are imposed MVP requirements, not spreadsheet-derived privileges.
2. Create/edit/save draft and submit V3 reports with grouped deployment, location/surgery, navigation performance/use, issue categories, surgeon feedback, internal/hospital requests, loss/damage, and external document-link fields. Preserve all 49 columns, especially R/X duplicates and AV opaque metadata. Distinguish surgery success from navigation usefulness as V3 explicitly requests.
3. Read/edit older V1/V2 records using their schema. V1-specific deployment/removal dates, costing/action/feedback fields and V2 legacy summaries remain available rather than disappearing in a V3-only model.
4. Search/filter/paginate report lists; filter date range, hospital/city/surgeon/system text, surgery type, system identity/base, status and owner subject to role visibility. Export the same authorized filtered results as formula-safe CSV with explicit availability states.
5. Admin preview and explicitly commit historical XLSX imports for all three versions, including V1 inventory and extra-provided ledgers. Handle sparse/shared/inline cells, Excel serial dates and epoch, blank rows, sentinels and quantity codes. Preview is read-only, commit atomic, imports idempotent, source provenance retained. No startup ingestion or overwriting by fuzzy matching.
6. Maintain system current location/hospital/expert/issues/readiness and categorized items/quantities/availability. Record additional-instrument ledger date, provider, quantity, reference/cost separately. Historical stock reconciliation is unavailable and must not be invented.
7. Reviewer/admin comments author-stamped and immutable; historical reviewer-comment text remains a source field distinct from new comments. Audit mutations/imports/user changes without copying sensitive text into audit logs.
8. Attachment fields support explicit external HTTPS links only. No uploading patient images, fetching/proxying linked content, thumbnail rendering or access assertions.

## Source semantics and contradictions

- V3 I observed categories: Cranial, CT-Spine, X-Ray Spine, Biopsy (cranial/full body), ENT, Other. O navigation Completely/Partially/Not used; AH Optical/EM; M Yes/No; AW verbose yes/no customer-location values. Normalize exact known values, preserve unmatched raw data with warnings.
- V2/V3 accuracy headers explicitly use 100.00 for unavailable; X-ray headers use 1000 for not-applicable OR unknown. Keep state unknown/raw, exclude from numeric calculations; do not assign an invented cause. Text NA can mean no issue/no feedback; ordinary blanks are not recorded, not proof of absence.
- Inventory quantity AV indicates available and NA indicates unavailable, supported by missing-instruments status notes; neither is a numeric count. Retain null quantity separately from availability. Actual zero must remain zero.
- V1 legend: green ready, red not ready, blue latest update. Blue is revision metadata, not a third readiness status. Colour or heading conflicts must be reported rather than silently resolved.
- Several V1 sheet names, title cells and current-location blocks disagree (Hyderabad/Kolkata; Trivandrum/Mumbai; Mumbai/Delhi). Preserve source metadata and warn; present an unknown/readiness state pending human reconciliation.
- Dates combine Excel numeric serials and textual dates; ledger reference/challan notes appear in date-column cells. Preserve reference notes separately. Workbook timestamps do not establish a timezone.
- V2 broad narrative issues/feedback plus later individual categories coexist. V3 software issue R and X labels overlap; preserve both. V3 AV Column 47 purpose is unknown. Original labels/column provenance retained; no speculative semantic consolidation.
- Equipment serial strings are identities, not quantities. Extra-provided rows have dates/provider/cost only on some lines; missing dates/cost/currency are unknown and cannot be filled automatically.

## Nonfunctional requirements and security

Local localhost-bound single-process deployment; durable SQLite transactions/restart persistence; parameterized SQL; optimistic versions; bounded request/import/ZIP sizes; whitelisted static files. Cookie sessions, password hashing, CSRF/Origin protection including login, throttling, role/object authorization, immediate invalidation upon account changes, private no-store responses. Render user text inert; external links secure protocol/opener handling; CSV cells cannot execute spreadsheet formulas. No historical personal/surgery data in startup seed, screenshots, docs or public UI artifacts. Imported data lives privately in runtime database. Production hosting, jurisdiction/retention policy, encryption at rest and clinical approval are unresolved release gates.

## MVP assumptions and missing information

Draft/submitted status workflow and required submission fields are product assumptions explicitly documented in architecture/contracts.md; workbook validation rules were absent. Admin selects engineer owner for an imported workbook; staff-name/email auto-account mapping is out of scope and would be error-prone. Legacy forms can be edited without forcing new required V3 fields. No hard delete, clinical scoring, surgery recommendations, automated notifications or inventory stock movement reconciliation. Unknown currency displayed unspecified. Production identity provider, MFA, deployment topology, expected load, attachment permissions, patient-data minimization, retention/backup ownership and fine-grained historical report assignment need user decisions before production use; none blocks bounded local implementation.

## Acceptance and delivery plan

Contracts in docs/architecture/contracts.md govern schemas, persistence/functions, API payloads and permissions. Database/parser, backend and frontend can proceed concurrently after reading that contract; shared interface changes go through primary agent. QA independently verifies permission matrix, legacy import/date/sentinel/idempotency/rollback, V3 completeness, filtered formula-safe export, session/error paths and persistence. Security/reviewer inspect before final verification; resolve blocker/high findings. Real tests and browser verification must be reported accurately. Acceptance requires all version field metadata, all V3 fields in UI/store/export, six inventory structures with availability/readiness/ledger handling, authenticated CRUD/comments, explicit historical import, provenance and audit; raw source workbooks unchanged. README documents setup, tests, private data location and local-server limitation. No production release is claimed.

The supplied references are populated data workbooks rather than UI mockups; styling does not establish an application navigation or interaction design. The V1 explicit colour legend informs textual readiness labels, never colour-only UI. No separate written requirements or design mockups were present in docs/reference at inspection time.
